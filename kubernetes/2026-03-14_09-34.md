 # Kubernetes Concept
This is an example of a Kubernetes DaemonSet configuration for running a logging agent, such as Fluentd, on every node in a cluster.

# Explanation
A DaemonSet ensures that a specified number of replicas of a pod are running on each node in the cluster, making it an ideal choice for running system daemons or agents like logging agents. In this instance, we will configure a Fluentd DaemonSet using Helm and Kubernetes.

# Best Practices
- Use Helm charts for managing dependencies and configuration.
- Configure the DaemonSet to use the latest stable version of the container image.
- Set appropriate resource limits and requests for the containers.

# YAML Example
```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: fluentd
  labels:
    app: fluentd
spec:
  selector:
    matchLabels:
      app: fluentd
  template:
    metadata:
      labels:
        app: fluentd
    spec:
      securityContext:
        privileged: true
      containers:
      - name: fluentd
        image: fluentd:v1.17.2-1
        ports:
        - containerPort: 24224
          protocol: TCP
        volumeMounts:
        - mountPath: /var/log
          name: var-log
        - mountPath: /run/fluentd
          name: fluentd-run
        - mountPath: /etc/fluentd
          name: etc-fluentd
        resources:
          limits:
            cpu: "1"
            memory: "256Mi"
          requests:
            cpu: "100m"
            memory: "50Mi"
      volumes:
      - name: var-log
        hostPath:
          path: /var/log
      - name: fluentd-run
        emptyDir: {}
      - name: etc-fluentd
        configMap:
          name: fluentd-config
```
This YAML example creates a DaemonSet named `fluentd` that runs a single container of `fluentd:v1.17.2-1`. It sets the desired number of replicas to 1, ensuring that one instance of the container will run on each node. The container is configured to mount the host's `/var/log` directory, create an empty `/run/fluentd` directory, and use a `configMap` named `fluentd-config` for storing and managing its configuration files. The container runs with privileged access and has specified resource requests and limits.
