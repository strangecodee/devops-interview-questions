# Best Practice: Implement Multi-stage Builds in Docker
Use multi-stage builds to keep the runtime image as lean as possible by separating the build environment from the final image.

# Explanation
Multi-stage builds allow you to build an image using one Dockerfile and then use a second Dockerfile to create a runtime image from the build image. This means that the runtime image only includes the necessary files and dependencies, reducing the image size and improving the overall application performance.

# Why It Matters
- Reduces image size: By only including the required files and dependencies in the runtime image, you can significantly reduce the image size, which leads to faster build and deployment times.
- Improves security: By separating the build environment from the runtime image, you can ensure that sensitive information, such as build tools, remains in the build image and is not carried over to the runtime image.
- Enhances maintainability: Multi-stage builds make it easier to maintain and update your application, as any changes to the build environment or dependencies do not affect the runtime image.

# Example
```Dockerfile
# Build stage
FROM node:14-alpine AS build-env
WORKDIR /app
COPY package.json yarn.lock ./
RUN yarn install
COPY . .
RUN yarn build

# Runtime stage
FROM nginx:latest
COPY --from=build-env /app/dist .
EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]
```
In this example, the first stage is used for building the application using Node.js and the second stage is used to create the runtime image based on the Nginx server, which serves the built application. The `COPY --from=build-env` command is used to copy the compiled files from the build stage to the runtime stage.
