 # Docker Image Security Best Practice: Use Multi-stage Builds
Use multi-stage builds to minimize attack surface by keeping the runtime image as small and lean as possible, and separating the build tools and dependencies from the final image.

# Explanation
Multi-stage builds allow you to create a Docker image using multiple Dockerfiles in sequence, each one building on top of the previous one. The final image is based on the last Dockerfile, while the build artifacts and dependencies of the previous stages are discarded. This approach reduces the image size and minimizes the attack surface by keeping the runtime image clean.

# Why It Matters
- Reduces the image size, resulting in faster downloads and less storage consumption.
- Minimizes the attack surface by removing unnecessary tools and libraries from the runtime image.
- Facilitates easier security updates and patching by allowing you to update and patch only the build stage, without affecting the runtime image.

# Example
```Dockerfile
# Stage 1: Build
FROM golang:alpine AS build
RUN apk update && apk add --no-cache golang
WORKDIR /app
COPY . .
RUN go build .

# Stage 2: Runtime
FROM alpine:latest
RUN apk add --no-cache --virtual .build-dependencies \
  curl \
  jq \
  && run apk del .build-dependencies
COPY --from=build /app/main /app/
ENTRYPOINT ["/app/main"]
```
In this example, the first stage is used for building the application using Go, and the second stage is used as the runtime image. The build stage is not included in the final image, minimizing the attack surface and reducing the image size.
