 # Best Practice: Use Multi-Stage Builds for Docker Images
Use multi-stage builds to create Docker images that maintain a small attack surface and improve build performance, by separating the build environment from the runtime environment.

# Explanation
Multi-stage builds allow you to define multiple build stages in a single Dockerfile. Each stage can have its own set of instructions for installing dependencies, compiling code, or creating artifacts. The final image is then built using the last stage. This approach cleans up unnecessary artifacts from the final image, reducing its size and attack surface.

# Why It Matters
- Reduced Attack Surface: By separating the build environment from the runtime environment, you minimize the number of unnecessary packages and libraries in your final image. This, in turn, reduces the attack surface of your container.
- Improved Build Performance: Multi-stage builds eliminate the need to install and manage development tools within the production image. This results in faster builds as you are only installing the required tools for the build process, not the entire runtime environment.
- Enhanced Security: By using multi-stage builds, you can ensure that development and production environments are kept separate, reducing the risk of introducing vulnerabilities from development tools into your production environment.

# Example
```Dockerfile
FROM node:14 AS build-env
WORKDIR /app
COPY package*.json ./
RUN npm install
COPY . .
RUN npm test

FROM nginx:latest
COPY --from=build-env /app/package.json /etc/nginx/conf.d/
COPY --from=build-env /app/nginx.conf /etc/nginx/
COPY --from=build-env /app/ /usr/share/nginx/html
EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]
```
In this example, the first stage installs Node.js, runs the tests, and copies the application code. The second stage uses the Nginx base image and copies the necessary configuration files and the compiled application from the first stage to serve the application. This results in a smaller final image with only the required packages without the development tools that were used during the build process.
