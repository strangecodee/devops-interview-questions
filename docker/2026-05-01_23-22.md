# Best Practice: Minimize Docker Image Size with Multi-Stage Builds
Create multi-stage builds to separate the build environment from the runtime environment, minimizing the final image size.

# Explanation
Multi-stage builds allow you to define multiple build stages in a single Dockerfile, each one based on a different base image. The first stage sets up the build environment, installs dependencies, and compiles the application. The second stage creates a smaller runtime image that only includes the application and its dependencies.

# Why It Matters
- Minimizing image size reduces the time required to download and install images, improving the overall build and deployment process.
- Larger images increase the risk of security vulnerabilities, as they potentially include more external packages, some of which might not be needed.
- Faster image builds lead to quicker testing and delivery, aligning with continuous integration and continuous delivery (CI/CD) best practices.

# Example
```Dockerfile
# Stage 1: Build environment
FROM node:12.18.3-alpine as builder
WORKDIR /app
COPY package.json yarn.lock ./
RUN yarn install
COPY . .
RUN yarn build

# Stage 2: Runtime environment
FROM node:12.18.3-alpine
WORKDIR /app
COPY --from=builder /app/dist .
EXPOSE 3000
CMD ["npm", "start"]
```
In this example, we use a multi-stage build with Node.js to separate the build environment (`node:12.18.3-alpine`) and the runtime environment (also `node:12.18.3-alpine`). The first stage installs dependencies, compiles the application, and copies the compiled files to the second stage. The resulting runtime image is much smaller than it would be if we had included the dependencies in the runtime image as well.
