 # Interview Question
How would you approach implementing zero-downtime deployments using Kubernetes and Rollouts?

# Answer
Zero-downtime deployments are crucial for maintaining application availability and minimizing user disruption. In the context of Kubernetes, Rollouts provide a mechanism to achieve this by gradually rolling out updates to a percentage of replicas, while monitoring and inspecting their health.

To implement zero-downtime deployments using Kubernetes and Rollouts, follow these steps:

1. Create a new deployment with the updated version of the container image.
2. Use the `kubectl set image` command to update the running pods' container image to the new deployment without changing its active replicas.
3. Kubernetes will replace old pods with new ones during the update process, with Rollouts ensuring that the number of available replicas is not reduced below the minimum replica count.
4. After all new pods have successfully passed the readiness and liveness probes, Rollouts will incrementally route traffic to them.
5. Once all traffic is routed to the new pods, Rollouts will declare the old pods as out of service and delete them.

# Key Technical Points
- Employs a phased approach to updating pods, maintaining availability during the deployment process.
- Uses rolling updates to minimize downtime and ensure a smooth transition from old to new pods.
- Monitors pod health with readiness and liveness probes, ensuring only healthy pods receive traffic.

# Real-World Example
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 3
  selector:
    matchLabels:
      app: my-app
  template:
    metadata:
      labels:
        app: my-app
    spec:
      containers:
      - name: my-app-container
        image: old-image:latest
        ports:
        - containerPort: 80
      --containers:
      - name: my-app-container
        image: new-image:latest
        ports:
        - containerPort: 80
      strategy:
        type: RollingUpdate
        rollingUpdate:
          maxSurge: 1
          maxUnavailable: 0
```
In this example, a Deployment named 'my-app' is created with three replicas, two of which run the old image and one the new image. The `rollingUpdate` strategy is set with `maxSurge` as 1 (one new replica at a time) and `maxUnavailable` as 0 (no old replicas can be deleted until new ones are ready). Once new replicas are ready and healthy, traffic is gradually routed to them, and the old replicas are deleted.
