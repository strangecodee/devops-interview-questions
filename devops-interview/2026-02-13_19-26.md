 # Interview Question
Can you explain how to secure a Kubernetes cluster using RBAC and network policies?

# Answer
RBAC (Role-Based Access Control) and network policies are two essential security features in Kubernetes that help secure the cluster from unauthorized access and potential network attacks. RBAC allows defining roles and permissions for users, groups, and services, while network policies help control the flow of network traffic within the cluster.

# Key Technical Points
- RBAC enables defining roles and permissions for users, groups, and services, ensuring that only authorized entities can interact with the Kubernetes resources.
- Network policies help control the traffic flow between different pods and services within the cluster based on labels, source and destination IP addresses, ports, and protocols.
- Both RBAC and network policies are declarative, meaning that the desired state is defined in manifests or YAML files, and Kubernetes automatically enforces these policies.

# Real-World Example
Suppose we have a Kubernetes cluster with multiple applications, and we want to allow the application `app1` to access the database `db` only through a specific port (3306). In this scenario, we would create the following YAML manifests:

```yaml
# Role and RoleBinding for app1
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: app1-role
  namespace: default
rules:
- apiGroups: [""]
  resources: ["services"]
  verbs: ["get"]

---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: app1-role-binding
  namespace: default
subjects:
- kind: ServiceAccount
  name: default-app1
roleRef:
  kind: Role
  name: app1-role
  apiGroup: rbac.authorization.k8s.io

---
# Network Policy for app1 to access the database
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: app1-network-policy
  namespace: default
spec:
  podSelector:
    matchLabels:
      app: app1
  ingress:
  - ports:
    - protocol: TCP
      port: 3306
    from:
    - podSelector:
        matchLabels:
          app: db
    - ipBlock:
        cidr: 0.0.0.0/0
      ports:
      - protocol: TCP
        port: 3306
  egress: []
```

With these manifests in place, `app1` will be able to access the database through the allowed port, while all other traffic will be blocked. Additionally, `app1` will have the necessary permissions to interact with the services within the cluster.
