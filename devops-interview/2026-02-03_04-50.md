 # Interview Question
Can you explain the process of securing a Kubernetes cluster using RBAC and network policies?

# Answer
RBAC (Role-Based Access Control) and network policies are two essential security features in Kubernetes that help in securing a cluster. RBAC provides access control for Kubernetes API resources, while network policies manage the communication between pods in the cluster. First, we create RBAC roles and bind appropriate privileges to them. Then, we create RBAC role bindings that assign roles to users or service accounts. Lastly, we apply network policies to restrict pod-to-pod and pod-to-service communication based on source and destination pod selectors, labels, and names.

# Key Technical Points
- RBAC: Provides access control for Kubernetes API resources (pods, deployments, services, and secrets), securing the cluster from unauthorized access and modification.
- Network Policies: Implementation of Mandatory Access Control (MAC) for Kubernetes, allowing communication only between approved sources and destinations, reducing potential attack vectors.
- Creating RBAC roles: Define the access level and permissions for the role (cluster-admin, edit, view, or create).
- Creating RBAC role bindings: Assign RBAC roles to users or service accounts, ensuring only authorized entities have access to the cluster.
- Defining network policies: Implement policies using labels, selectors, and conditions to restrict communication and maintain a secure network topology.

# Real-World Example
Let's consider a Kubernetes cluster named "nebula," running on AWS EKS. We'll create RBAC roles and bindings for a developer named "john," and apply network policies to restrict communication between pods with specific labels:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: john-role
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "watch", "list"]
  resourceNames: []

---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: john-binding
subjects:
- kind: User
  name: john
roleRef:
  kind: Role
  name: john-role
  apiGroup: rbac.authorization.k8s.io

---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: nebula-policy
spec:
  podSelector:
    matchLabels:
      app: nebula
  policyTypes:
  - Ingress:
    - from:
      - podSelector:
          matchLabels:
            app: db
        ports:
        - protocol: TCP
          port: 3306
```

In this example, we created a "john-role" with "get", "watch", and "list" permissions on pods. Then, we created a "john-binding" to bind the role to the user "john." Lastly, we created a network policy "nebula-policy" that allows communication between pods with the label "app: nebula" and pods with the label "app: db" on port 3306. This policy ensures secure communication between the "nebula" and "db" pods in the "nebula" cluster.
